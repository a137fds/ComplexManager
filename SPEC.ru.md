# ComplexManager — Техническое задание

## 1. Обзор проекта

ComplexManager — веб-приложение для управления жилым комплексом (site) в Турции.

Система создаётся непосредственно для жилого комплекса. Управляющая компания является одной из ролей системы, а не владельцем системы.

## 2. Аутентификация

- Пользователи проходят аутентификацию по логину и паролю.
- В качестве логина может использоваться адрес электронной почты пользователя.
- Первоначальные пароли генерируются системой.
- Первоначальные данные для входа могут быть отправлены пользователям по электронной почте.
- После входа пользователь может изменить свой пароль.

## 3. Роли

### 3.1 Admin

Полный доступ ко всем функциям и данным системы.

### 3.2 Management Company

Управляющая компания работает с комплексом в пределах разрешений, назначенных этой роли.

Management Company не может физически удалять документы. При использовании действия удаления документ вместо физического удаления помечается как удалённый.

Удалённые документы:

- скрыты от Management Company;
- скрыты от всех остальных ролей, кроме Admin;
- остаются видимыми для Admin как удалённые элементы;
- должны сохранять информацию о том, что они были помечены на удаление управляющей компанией.

### 3.3 Chairman

Председатель правления комплекса.

### 3.4 Board Member

Член правления комплекса.

### 3.5 Financial Controller

Отвечает за функции финансового контроля, назначенные ему разрешениями системы.

### 3.6 Site Staff

Сотрудник комплекса, выполняющий операционные и хозяйственные задачи, включая такие функции, как турецкий kapıcı.

### 3.7 User

Жилец жилого комплекса.

### 3.8 Guest

Неавторизованный посетитель сайта.

Guest является полноценной ролью системы с собственными разрешениями, несмотря на то, что гость не проходит аутентификацию.

Например, Guest может иметь следующие разрешения:

- просмотр главной публичной страницы;
- просмотр общих фотографий комплекса.

Полный набор разрешений Guest будет определён позднее.

## 4. Локализация и многоязычность

Приложение с самого начала должно проектироваться как многоязычная система. Интернационализация и локализация должны быть частью первоначальной архитектуры, а не функцией, добавляемой после разработки основной системы.

На момент запуска система должна поддерживать следующие языки:

- русский;
- английский;
- французский;
- турецкий;
- датский;
- шведский;
- польский.

Архитектура должна позволять добавлять новые языки в будущем без переработки приложения или существующей модели контента.

### 4.1 Выбор языка

На главной странице должен быть доступен переключатель языка. Переключатель должен быть доступен пользователю последовательно и удобно на протяжении всего сайта.

Переключатель должен быть выполнен в виде элемента с флагом или другого понятного визуального элемента выбора языка. При нажатии должен открываться список доступных языков с соответствующими флагами.

### 4.2 Подготовленные переводы

Для всего интерфейса и системного контента, требующего перевода, приложение должно использовать заранее подготовленные переводы для каждого поддерживаемого языка.

Автоматический перевод браузером или сторонним сервисом машинного перевода (например, Google Translate) не должен использоваться как основной механизм локализации. Это особенно важно для технической, административной, финансовой, юридической и другой контекстно-зависимой информации, где некорректный перевод может изменить смысл.

Переводы должны храниться и управляться как часть системы локализации приложения, чтобы для каждого поддерживаемого языка существовал собственный проверенный текст.

## 5. Модель разрешений

Система будет использовать ролевую модель разрешений (RBAC).

Для каждой защищённой страницы или функциональной области должны существовать соответствующие разрешения. Разрешения назначаются ролям, включая роль Guest.

Подробная матрица разрешений будет определена на этапе формирования требований.

## 6. Статус требований

Данный документ является живым техническим заданием. По мере обсуждения проекта требования будут добавляться, уточняться и изменяться.
