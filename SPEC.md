# ComplexManager — Technical Specification

## Status model

Each requirement has one status:

- **Proposed** — captured but not yet approved as final.
- **Approved** — explicitly agreed and ready for implementation.
- **Implemented** — present in the repository/database, but not yet fully verified by user or end-to-end testing.
- **Verified** — implementation has been checked against the requirement and is considered complete.

This document is the source of truth. New requirements are first formulated from the user's raw description, then approved, recorded here, implemented, and finally verified.

## 1. Project and architecture

- **Implemented** — ComplexManager is a web application for managing a residential complex (site) in Türkiye.
- **Approved** — The management company is a role within the residential complex system, not the owner of the system.
- **Approved** — Multilingual support and role-based permissions are first-class architectural concerns.
- **Approved** — Adding a language must not require rewriting existing pages/forms.
- **Approved** — Permission checks should be centralized and reusable rather than duplicated as ad-hoc role checks throughout the UI.

## 2. Authentication

- **Implemented** — Supabase Authentication is used.
- **Implemented** — Users can sign in with email and password.
- **Implemented** — Authenticated session is loaded and the user's profile/role is read from `user_profiles`.
- **Verified** — Deployed GitHub Pages authentication has been tested by the user and successfully reaches the application after the public Supabase key was corrected.
- **Approved** — Email may be used as the login identifier.
- **Approved** — Initial passwords are generated by the system.
- **Proposed** — Initial credentials are distributed to users by email.
- **Proposed** — Users can change their password after signing in.

## 3. Roles and permissions

### 3.1 Roles

The intended roles are:

- Admin
- Management Company
- Chairman
- Board Member
- Financial Controller
- Site Staff / Kapıcı
- User / resident
- Guest

- **Implemented** — The main authenticated roles exist in the application/profile model.
- **Implemented** — `roles`, `permissions`, `role_permissions`, and `user_roles` exist in Supabase.
- **Implemented** — Guest exists in the database permission matrix.
- **Proposed** — Guest permissions and public-access behavior require a dedicated final review.

### 3.2 Management Company document deletion

- **Implemented** — The UI contains soft-delete, restore, and Admin-only deleted-document views.
- **Implemented** — Management Company deletion is represented as soft deletion in the current application state.
- **Proposed** — Persist the document governance workflow fully in Supabase and enforce it server-side.
- **Proposed** — Deleted documents must be hidden from all non-Admin roles and remain visible to Admin as deleted records.
- **Proposed** — The database must retain who marked a document for deletion and when.

### 3.3 Central permission enforcement

- **Implemented** — A database role/permission matrix exists and the Administration UI loads and saves it.
- **Implemented** — The matrix contains permissions for Complex, Buildings, Residents, Billing, Tasks, Documents, Administration and Audit.
- **Proposed** — All protected routes, navigation items and operations must actually enforce the database permission matrix rather than hard-coded role-name checks. The current UI still contains direct role checks in several components.
- **Proposed** — Permission checks must also be enforced by the backend/API/RLS, not only by hiding UI controls.

## 4. Localization and multilingual support

### 4.1 Supported languages

- **Implemented** — English, Russian, Turkish, French, Danish, Swedish and Polish are represented in the localization system.
- **Implemented** — A central translation dictionary exists.
- **Approved** — Additional languages must be addable without redesigning existing pages/forms.
- **Proposed** — Complete localization audit must be finished for every user-facing component and every supported language.

### 4.2 Language selector

- **Implemented** — The authenticated application has a language selector in the header.
- **Implemented** — The current selected language is passed through the application to the main views.
- **Implemented** — A persisted `default_language` exists on `user_profiles` with default `en`.
- **Implemented** — On profile load, the UI initializes `currentLang` from `profile.default_language`.
- **Implemented** — Selecting a different language offers to save it as the default language.
- **Proposed** — The selector should be consistently available on all required public/guest pages as well as authenticated pages where appropriate.

### 4.3 Default language and invoice language

- **Implemented** — `user_profiles.default_language` exists in Supabase and defaults to English.
- **Implemented** — The application reads the persisted default language when the profile is loaded.
- **Implemented** — The user is asked whether the newly selected language should become the default for the website and documents.
- **Implemented** — A saved default language controls the initial website language.
- **Proposed** — Admin, Management Company and Chairman must be able to change another user's default language through a dedicated permission and UI. The database permission for this is not yet implemented.
- **Proposed** — Generated invoices/receipts must use the invoice recipient's persisted default language.
- **Proposed** — Multiple invoice recipients must each receive the same financial invoice rendered in their own default language.

### 4.4 Translation rules for user data and Turkish terminology

- **Implemented** — Complex/site names, addresses and building names are treated as stored user data in the current Complex/Buildings UI rather than being passed through the language dictionary.
- **Implemented** — `Complex (Site)` is treated as a special UI term with `Site` retained unchanged.
- **Implemented** — Building terminology was corrected so that residential buildings are not translated as construction materials/blocks.
- **Implemented** — `Kapıcı` is retained where the project requires the original Turkish terminology.
- **Approved** — Apartment/unit identifiers and other free-form user-entered identifiers must never be automatically translated.
- **Proposed** — The same rule must be audited across every remaining screen, including documents, residents, billing, tasks and invoices.

### 4.5 Complete localization audit

- **Proposed** — Every user-facing string must use the central localization system.
- **Proposed** — Hard-coded English in user-facing components must be replaced with localization keys.
- **Proposed** — Validation, errors, confirmations, loading states, empty states, tables, filters, administration, billing and invoice UI must be audited for all seven languages.
- **Proposed** — Switching language must never leave a confusing mixture of languages in the visible interface.

## 5. Main layout and navigation

- **Implemented** — Dashboard layout contains header, left navigation and main content area.
- **Implemented** — The technical `Cloud SQL (CRUD)` screen is no longer part of the user-facing navigation.
- **Implemented** — The first screen is `Start Page` / `Обзор` rather than the technical CRUD screen.

### 5.0 Start Page / Overview

- **Implemented** — Start Page exists.
- **Implemented** — It displays accessible complex/building summary cards using the currently loaded Complex and Buildings API data.
- **Implemented** — The cards navigate to Complex and Buildings.
- **Proposed** — Counts must be guaranteed to be permission/data-scope aware for every role; the current API/UI loads broad lists and does not yet demonstrate full per-user scope enforcement.
- **Approved** — Technical CRUD is not a product feature. Its useful summary information belongs on Start Page.

### 5.1 Complex (Site)

- **Implemented** — Complex list/view exists and reads from the database API.
- **Implemented** — Create, edit and delete actions are connected to the API.
- **Implemented** — Create/Edit accepts Complex Name and Address without a user-ID form field.
- **Implemented** — Acting identity is supplied through the authenticated API session rather than a form `UserID` field.
- **Proposed** — Server-side authorization must verify that the authenticated user has the corresponding permission.
- **Proposed** — Photos/documents and all related complex-level resources must be fully persistent and permission-controlled.

### 5.2 Buildings

- **Implemented** — Buildings list/view exists and reads from the database API.
- **Implemented** — Create, edit and delete actions are connected to the API.
- **Implemented** — Create/Edit no longer exposes `Change User ID` / `ChangeUserID`.
- **Implemented** — Building names are displayed as stored data and are not translated.
- **Implemented** — Residential-building terminology was corrected in the UI.
- **Proposed** — Server-side permission enforcement and complete resource associations must be finished.

### 5.3 Residents

- **Implemented** — Residents view exists in the application.
- **Implemented** — The UI contains resident, invoice and payment information and supports opening invoice details.
- **Proposed** — Resident visibility must be enforced by actual ownership/association and permissions rather than relying on the current in-memory/demo data.
- **Proposed** — Resident financial calculations must use persistent invoice/payment records as the source of truth.

### 5.4 Administration

- **Implemented** — Administration view exists.
- **Implemented** — Role/permission matrix is loaded from Supabase and can be changed and saved to `role_permissions`.
- **Implemented** — Audit log UI exists.
- **Implemented** — Raw UUIDs are not intended as the visible change-user value in the current Buildings UI; Admin-only change metadata behavior has been added there.
- **Proposed** — Administration access itself must be enforced through permissions, not only by UI navigation.
- **Proposed** — Human-readable change-user names should come from an actual user/profile display-name field when that model is defined; role labels are not a substitute for a person's name.

## 6. Billing, annual charges and invoices

### 6.1 Annual charges

- **Implemented** — Billing UI contains an annual-charge creation form and Year/Amount fields.
- **Implemented** — Billing UI has management controls for Admin/Management Company/Chairman by current role check.
- **Proposed** — Annual charges must be persisted in Supabase through the application API rather than only kept in React state.
- **Proposed** — The final permission matrix, not hard-coded role names, must control annual-charge management.

### 6.2 Send to All

- **Implemented** — `Send to All` exists in the Billing UI and generates individual invoice objects in the current application state.
- **Proposed** — The operation must create persistent invoice records in Supabase.
- **Proposed** — PDF documents must actually be generated and stored.
- **Proposed** — Each apartment/unit must receive its own full invoice.
- **Proposed** — The system must send the generated document to configured invoice recipients by email.
- **Proposed** — Generated invoices must remain historical records and must not silently change if an annual charge changes later.

### 6.3 Billing history and payments

- **Implemented** — The application has separate invoice and payment structures in the current model/UI.
- **Implemented** — Billing UI calculates total billed, paid and outstanding values from the current application data.
- **Proposed** — Invoice and payment records must be fully persistent and related through the database.
- **Proposed** — One resident/user must support many invoices and many payments over time.
- **Proposed** — The database records must be the source of truth for financial summaries.

### 6.4 Invoice access

- **Implemented** — Residents/Billing views can open invoice details in the UI.
- **Proposed** — Invoice access must be enforced by persistent ownership/association and permissions so a resident cannot access another resident's financial documents.

### 6.5 Multiple owners and invoice recipients

- **Approved** — One user may be associated with multiple apartments/units.
- **Approved** — One apartment/unit may have multiple owners/users.
- **Proposed** — Current database must be migrated from the existing one-user/one-resident association to a dedicated many-to-many user↔unit relationship.
- **Proposed** — Ownership/association must be independent from invoice-recipient configuration.
- **Proposed** — One or more associated users may be explicitly selected as invoice recipients.
- **Proposed** — An invoice is never divided between owners; every selected recipient receives the full invoice amount as their copy.
- **Proposed** — Invoice-recipient configuration must be controlled by a dedicated permission.
- **Proposed** — Recipients must receive invoices in their own default language.

## 7. Data and persistence architecture

- **Implemented** — Supabase/PostgreSQL is used for core entities including complexes, buildings, residents, invoices, payments, documents, roles and permissions.
- **Implemented** — `user_profiles.default_language` exists in the database.
- **Implemented** — Change-user/change-date fields exist on core records such as complexes and buildings.
- **Proposed** — User↔unit ownership/association must be represented by a dedicated many-to-many table.
- **Proposed** — Invoice-recipient relationships must be represented explicitly in the data model.
- **Proposed** — Invoice records must relate to units and recipients rather than using a single resident field as the complete ownership model.
- **Proposed** — Documents/photos/PDFs must use persistent object storage with database metadata and relationships.
- **Proposed** — Full database/RLS/API authorization must match the permission model.

## 8. Permission model

- **Implemented** — Database roles and permissions exist.
- **Implemented** — Role-to-permission assignments exist in `role_permissions`.
- **Implemented** — Administration UI can display and save the matrix.
- **Implemented** — Dedicated database permissions for many major functional areas exist.
- **Proposed** — Dedicated permissions must be added for changing another user's default language and configuring invoice recipients.
- **Proposed** — Every protected page, navigation item and operation must use the permission model.
- **Proposed** — Financial access must include ownership/association checks.
- **Proposed** — Guest must be handled as an actual public permission role without requiring authentication.

## 9. Specification workflow

- **Implemented** — `SPEC.md` is used as the project specification and has been reconstructed from the development discussion.
- **Implemented** — Status model is now defined as Proposed → Approved → Implemented → Verified.
- **Implemented** — New requirements are intended to be formulated and approved before implementation.
- **Approved** — Implementation audit is performed by comparing this specification against the actual repository and Supabase database.
- **Implemented** — This revision is the result of the first implementation audit.

### 10.3 Status interpretation

`Implemented` means the feature is present in the code/database but has not necessarily been end-to-end verified.

`Verified` is intentionally used sparingly. It requires an actual check against the requirement, and for interactive behavior it should normally include successful user testing. The user has already verified the deployed authentication flow and the current general application operation, but most requirements below remain `Implemented` or `Proposed` until their specific behavior is tested.

## 12. Next development rule

When a new feature is requested:

1. User gives the requirement in raw form.
2. Assistant formulates it as a precise requirement.
3. User approves or corrects the formulation.
4. Approved requirement is written to `SPEC.md` with status `Approved`.
5. Implementation begins.
6. After implementation the status becomes `Implemented`.
7. After repository/database review and appropriate user testing it becomes `Verified`.

No requirement should be silently skipped or considered complete merely because adjacent functionality exists.
